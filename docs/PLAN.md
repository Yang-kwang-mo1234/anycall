# anycall: Windows 동영상 실시간 번역 자막 (온디바이스, Rust)

> 2026-11-12에 주제를 바꿨다. 이전 계획(iOS/macOS/Windows 음성→텍스트 앱, Tauri v2)은 폐기하고 git 이력에만 남긴다.

## 목표
Windows에서 재생 중인 **영어 또는 일본어** 동영상의 소리를 받아, 화면 위에 **한국어 번역 자막**을 실시간으로 띄운다. 브라우저든 동영상 플레이어든 소리가 나는 프로그램이면 모두 대상이다. 인식과 번역은 모두 PC 안에서 처리하고 인터넷을 쓰지 않는다.

가장 중요한 품질 기준은 **자막이 나오는 속도**다.

| 측정 항목 | 목표 |
|---|---|
| 말이 시작된 뒤 첫 번역 자막이 보일 때까지 | 1.5초 이내 |
| 문장이 끝난 뒤 확정 자막이 보일 때까지 | 0.7초 이내 |
| 원문 부분 텍스트가 보일 때까지 | 0.5초 이내 |

두 언어 모두 같은 목표를 적용하고 따로 측정한다.

목표 수치는 0단계에서 이 PC로 측정해 달성 가능한지 확인하고, 안 되면 수치를 고쳐 적는다.

## 언어
원문 영어·일본어 → 자막 한국어 (사용자 확정, 2026-11-12). 다른 원문 언어는 이번 범위에 넣지 않는다.

- 원문 언어는 제어 창에서 **영어 / 일본어 중 하나를 고른다.** 언어를 고정하면 인식이 빠르고 정확하다.
- 자동 감지는 0단계에서 SenseVoice(구간마다 언어를 함께 알려 준다)를 고르게 되면 선택지에 추가한다. 다른 모델을 고르면 넣지 않는다.
- 한 동영상 안에서 두 언어가 섞여 나오는 경우는 자동 감지가 들어갈 때만 다룬다.

## 가정
요청에 없어서 아래처럼 정했다. 다르면 이 절부터 고친다.

- **하드웨어**: GPU 없이 CPU만으로 동작하는 것을 기본으로 한다. GPU 가속은 0단계 결과가 CPU로 부족할 때만 검토한다.
- **대상 OS**: Windows 10 2004 이상, x64만.
- **용도**: 개인 사용. 배포할 경우 모델 라이선스를 다시 확인한다(아래 위험 참고).

## 결정 사항
- **Rust 단일 실행 파일.** Tauri, WebView, Node.js를 걷어 낸다. crate 하나, 바이너리 하나다.
- **소리 입력: WASAPI loopback (`wasapi` crate).** 기본 출력 장치로 나가는 소리를 그대로 받는다. 마이크가 필요 없다.
  - `cpal`도 loopback을 받을 수 있지만 특정 프로그램 소리만 받는 기능이 없다. `wasapi` crate는 프로세스 지정 loopback(`new_application_loopback_client`)을 지원해 나중에 "이 플레이어 소리만" 받도록 넓힐 수 있다. 1차는 시스템 전체 소리만 받는다.
- **음성 구간 검출: Silero VAD.** 기존 모델 파일을 그대로 쓴다. 음악·무음 구간에서는 인식과 번역을 돌리지 않는다.
- **음성 인식: sherpa-onnx.** 기존 프로젝트에서 Windows 빌드와 동작을 확인한 엔진이다. 모델은 0단계에서 고른다. 두 언어를 한 모델로 처리하면 메모리와 언어 전환 시간이 줄지만, 언어별 모델이 더 정확하면 언어별로 둔다.
- **번역: 온디바이스 번역 모델.** 엔진과 모델은 0단계에서 고른다.
- **자막 화면: `eframe`(egui) 오버레이.** 테두리 없는 투명 창을 항상 위에 띄우고 마우스 입력을 통과시킨다. 한글은 `C:/Windows/Fonts/malgun.ttf`를 읽어 표시한다.
  - 오버레이는 클릭할 수 없으므로 시작/정지용 작은 제어 창을 따로 둔다(egui의 다중 viewport).

## 빠른 자막을 위한 설계
지연은 "소리 → 원문 텍스트 → 한국어 텍스트 → 화면" 세 구간에서 생긴다. 구간마다 아래처럼 줄인다.

1. **확정을 기다리지 않고 부분 번역을 먼저 보여 준다.** 문장이 끝나기 전에도 지금까지 인식된 원문을 번역해 흐린 색으로 보여 주고, 문장이 확정되면 확정 번역으로 바꾼다. 진행 중인 줄과 확정된 줄은 색으로 구분한다.
   - 일본어는 한국어와 어순이 거의 같아서 문장 앞부분의 번역이 뒤에서 크게 바뀌지 않을 것으로 기대한다.
   - 영어는 어순이 달라 부분 번역이 중간에 크게 바뀔 수 있다.
   - 둘 다 0단계에서 확인한다.
2. **번역은 항상 최신 텍스트만 처리한다.** 번역 스레드가 일하는 동안 들어온 부분 텍스트는 쌓지 않고 가장 최근 것 하나만 남긴다. 번역이 인식보다 느려도 자막이 밀리지 않는다. 확정 문장은 버리지 않고 반드시 번역한다.
3. **부분 번역 주기를 제한한다.** 원문이 일정량(영어 단어 3개, 일본어 8글자) 이상 늘었거나 마지막 번역에서 0.6초가 지났을 때만 부분 번역을 요청한다. 수치는 0단계 측정 뒤 조정한다.
4. **구간을 짧게 끊는다.** 침묵 0.4초, 최대 길이 6초 중 먼저 오는 것에서 구간을 확정한다(문장부호로 끊는 것은 뺐다, "0단계 결과" 참고). 구간이 짧을수록 인식·번역 한 번이 빨리 끝난다.
5. **모델은 시작할 때 한 번만 올린다.** 양자화(int8) 모델을 쓰고, 번역은 beam 크기 1~2로 돌린다.
6. **스레드를 나눈다.** 소리 입력, 인식, 번역, 화면이 서로를 기다리지 않는다.

자막은 소리보다 항상 늦게 나온다. 동영상을 늦춰 자막과 맞추는 기능은 넣지 않는다.

## 0단계: 모델 선택과 지연 측정 (구조를 만들기 전에)
속도와 품질은 직접 재야 알 수 있다. 콘솔 프로그램으로 영어와 일본어 음성(각각 대사가 있는 동영상 소리 2~3분, 16kHz wav)을 넣어 비교한다.

### 음성 인식 후보
모두 sherpa-onnx로 돌린다. 모델 이름과 제공 여부는 0단계를 시작할 때 sherpa-onnx 모델 목록에서 다시 확인한다.

| 후보 | 언어 | 방식 | 확인할 것 |
|---|---|---|---|
| SenseVoice small | 영어·일본어 (한 모델) | VAD 구간을 0.2초마다 다시 디코딩. 비자기회귀라 디코딩이 매우 빠르고 문장부호와 언어 정보가 나온다 | 두 언어의 정확도, 언어를 고정했을 때와 자동일 때의 차이 |
| Moonshine (tiny/base) | 영어, 일본어 (언어별 모델) | VAD 구간 재디코딩. 기존 `stt.rs`와 같은 방식이라 코드를 거의 그대로 쓴다 | 일본어 모델 제공 여부와 라이선스, 구간이 길어질 때 재디코딩 시간 |
| 스트리밍 Zipformer 영어 (`sherpa-onnx-streaming-zipformer-en-2023-06-26` 등) | 영어만 | 말하는 도중 토큰 단위로 결과가 나오는 진짜 스트리밍 | 대소문자·문장부호가 없으면 번역 품질이 떨어진다. 출력 형태를 먼저 확인한다 |
| Zipformer 일본어 (ReazonSpeech) | 일본어만 | VAD 구간 재디코딩. TV 방송 음성으로 학습 | 문장부호 출력 여부, 디코딩 시간 |

일본어 스트리밍 모델은 확인하지 못했다. 두 언어 결과가 비슷하면 모델 하나로 끝나는 SenseVoice를 고른다.

### 번역 후보
영→한, 일→한을 한 모델로 처리하는 후보를 우선한다.

| 후보 | 실행 방법 | 예상 |
|---|---|---|
| NLLB-200 distilled 600M (int8), `eng_Latn`/`jpn_Jpan`→`kor_Hang` | CTranslate2 (`ct2rs` crate) | 한 모델로 두 언어 처리. CPU에서 빠를 것으로 예상. 라이선스가 비상업(CC-BY-NC) |
| Opus-MT (영→한, 일→한 각각) | CTranslate2 (`ct2rs` crate) | 가장 작고 빠르지만 모델이 두 개 필요하고, 일→한 직접 모델이 있는지부터 확인해야 한다 |
| TranslateGemma 4B (Q4 GGUF, 약 2.5GB) | llama.cpp (`llama-cpp-2` crate) | 품질은 가장 좋을 것으로 기대. CPU만으로는 문장당 수 초가 걸릴 수 있어 GPU가 없으면 탈락 가능성이 높음 |

### 측정하고 기록할 것
- 인식: 부분 결과가 나오는 지연, 구간 확정 지연, 눈으로 본 정확도.
- 번역: 문장 길이별(영어 5·15·30단어, 일본어 10·30·60글자) 번역 시간, 번역이 자연스러운지, 문장 앞부분만 번역했을 때 결과가 전체 번역과 얼마나 달라지는지.
- 전체: 위 "목표" 표의 세 항목.
- CPU 사용률. 동영상 재생이 끊기면 안 된다.

### 결과에 따른 진행
- 목표를 채우는 조합이 여럿이면 번역 품질이 가장 좋은 것을 고른다.
- CPU로 목표를 채우는 조합이 없으면 GPU 가속(sherpa-onnx CUDA/DirectML, CTranslate2 CUDA, llama.cpp CUDA/Vulkan)을 측정하거나 목표 수치를 낮춘다. 어느 쪽으로 갈지는 결과를 보고 사용자와 정한다.
- `ct2rs`가 Windows에서 빌드되지 않으면(Windows 지원이 실험적이다) 번역 엔진을 llama.cpp 또는 ONNX Runtime으로 바꾼다.

결과는 이 문서에 "0단계 결과" 절을 추가해 적는다.

## 0단계 결과 (2026-11-12)
측정 환경: Intel Core i5-12500(6코어 12스레드), RAM 16GB, GPU 없음. 음성은 모델에 들어 있는 시험용 wav(영어 2개, 일본어 2개, 각 5~8초)를 실제 재생 속도로 흘려 쟀다. 대사가 있는 동영상 2~3분짜리로는 아직 재지 않았다(아래 "남은 측정").

### 고른 조합
- **음성 인식: Moonshine tiny, 언어별 모델** (`sherpa-onnx-moonshine-tiny-{en,ja}-quantized-2026-02-27`). `--model base`로 base 모델도 쓸 수 있다.
- **번역: NLLB-200 distilled 600M int8** (CTranslate2 변환본 `JustFrederik/nllb-200-distilled-600M-ct2-int8`), `ct2rs` 0.11 + Intel MKL, beam 1, 스레드 1.
- 자동 감지는 넣지 않았다(SenseVoice를 고르지 않았으므로).

### 음성 인식 비교
| 모델 | 영어 | 일본어 | 비고 |
|---|---|---|---|
| SenseVoice small int8 (2025-09-09) | 단어는 대체로 맞지만 전부 대문자, 문장부호 없음 | **틀림**: 한자만 늘어놓은 중국어식 출력(`家中学便当制持合五十円…`) | 탈락 |
| Moonshine tiny (en/ja) | 대소문자·문장부호 있음. "tribal chieftain" → "The travels used them" 같은 오인식 | 문장부호까지 거의 정확(`うちの中学は弁当制で持って行けない場合は、五十円の…`) | **선택** |
| Moonshine base (en/ja) | tiny보다 조금 정확(`50 pieces of gold`) | 글자 사이에 공백이 끼는 출력이 나옴 | 지연이 0.1~0.3초 더 큼. 선택 사항으로 둠 |
| Zipformer 영어 스트리밍, ReazonSpeech 일본어 | — | — | 재지 않음. Moonshine이 두 언어를 모두 충분히 처리해서 |

### 번역 시간 (NLLB 600M int8, 문장 하나, 3회 중 최소)
| 문장 | ruy 백엔드 | **MKL 백엔드** |
|---|---|---|
| 영어 4단어 | 2079ms | 330ms |
| 영어 11단어 | 2909ms | 480ms |
| 영어 24단어 | 8877ms | 1450ms |
| 일본어 11글자 | 2297ms | 370ms |
| 일본어 30글자 | 5563ms | 1000ms |
| 일본어 52글자 | 7216ms | 1190ms |

- `ct2rs` 기본 백엔드(ruy)는 x86에서 6배 느리다. MKL을 쓴다(`intel-onemkl-prebuild`가 nuget으로 받는다).
- 스레드 1·4·8, Intel OpenMP를 켠 빌드 모두 차이가 없었다. 문장 하나는 토큰을 하나씩 생성하는 시간이 대부분이라 병렬화가 효과가 없다. OpenMP는 DLL만 늘려서 쓰지 않는다.
- INT8이 INT16·FLOAT32보다 1.5~2배 빠르다.
- 번역 품질: 짧은 문장은 자연스럽다. "50엔짜리 학교용 빵을 사죠"처럼 뜻은 통하지만 주어·시제를 틀리는 경우가 있다. 모르는 토큰 `<unk>`는 자막에서 뺀다.

### 부분 번역 흔들림
- 영어: `If you had told me about` → "만약 당신이 나에게 이야기 했다", 문장 끝에서 "…일정을 재편했을 것입니다"로 크게 바뀐다. 예상대로 많이 흔들린다.
- 일본어: 앞 1/4(`子供の頃から住んでいたこの`)은 "이 작은 동네는"처럼 엉뚱하지만, 절반부터는 최종 번역과 거의 같다. 기대만큼은 아니지만 영어보다 안정적이다.
- 부분 번역은 끄지 않았다. 확정 문장이 들어오면 진행 중인 부분 번역을 생성 도중에 멈추고(CTranslate2 단계 콜백) 확정 문장을 먼저 번역한다. 이렇게 바꾸기 전에는 확정 지연이 1.1~3.0초(평균 1.9초)였다.

### 전체 지연 (wav 4개, Moonshine tiny)
| 항목 | 목표 | 측정 (평균 / 최대) | 판정 |
|---|---|---|---|
| 말 시작 → 원문 부분 텍스트 | 0.5초 | 0.27 / 0.30초 | 달성 |
| 말 시작 → 첫 번역 자막 | 1.5초 | 0.78 / 1.10초 | 달성 |
| 말 끝 → 확정 번역 | 0.7초 | 1.3 / 2.0초 | **미달** |

- 확정 지연은 침묵 판정 0.4초 + 구간 디코딩 0.05~0.25초 + 번역 0.4~1.5초다. 번역 시간이 문장 길이에 비례하므로 0.7초는 4~5단어 이하의 짧은 문장에서만 나온다.
- loopback으로 같은 영어 wav를 스피커로 재생해 받은 결과도 wav 직접 입력과 같았다(첫 번역 0.63초, 확정 1.8초). 소리 사이의 무음 구간에는 자막이 나오지 않았다.
- **확정 지연 목표를 어떻게 할지는 사용자와 정한다.** 선택지: (1) 목표를 "1.5초 이내"로 고친다, (2) 영어는 더 작은 Opus-MT(영→한)로 바꿔 잰다, (3) GPU 가속. 지금은 (1)을 가정하고 진행했다.

### 계획과 달라진 점
- **문장부호로 구간을 끊지 않는다.** 처음에는 SenseVoice의 토큰 시각으로 문장부호 위치에서 오디오를 자르게 만들었지만, Moonshine은 토큰 시각을 주지 않아 뺐다. 구간은 침묵 0.4초와 최대 6초로만 끝난다.
- 16kHz 모노 변환은 WASAPI의 autoconvert에 맡긴다(인식 스레드에서 따로 하지 않는다). wav 입력만 sherpa-onnx 리샘플러를 쓴다.
- 스레드 연결과 자막 상태는 `src/pipeline.rs`에 두었다. CMake·nuget을 PATH에 넣는 `scripts/build.ps1`을 추가했다.
- Windows 빌드 메모: sherpa-onnx 정적 라이브러리가 `/MT`라 `.cargo/config.toml`에서 `crt-static`을 켠다. `intel-onemkl-prebuild`는 코드에서 참조해야 MKL이 링크되므로 `main.rs`에 `use intel_onemkl_prebuild as _;`가 있다.

### 남은 측정
- 대사가 있는 실제 동영상(영어·일본어 각 2~3분)으로 정확도와 지연.
- 30분 연속 재생: 자막 밀림, 메모리 증가, 동영상 재생 끊김(CPU 사용률).
- 정지 후 다시 시작, 오버레이 아래 플레이어 조작(마우스 통과는 `WindowFromPoint`로 확인함).

## 구조
### 스레드와 데이터 흐름
```
[WASAPI loopback] --샘플--> [인식 스레드] --원문 텍스트--> [번역 스레드] --한국어 텍스트--> [화면]
   캡처 스레드                모노 변환·16kHz               최신 1건만 보관                  egui 오버레이
                              VAD → ASR                    (확정 문장은 큐)
```

1. **캡처 스레드**: 기본 출력 장치를 loopback으로 연다. 받은 샘플을 채널로 인식 스레드에 넘긴다.
2. **인식 스레드**: 채널을 모노로 합치고 16kHz로 바꾼 뒤 VAD에 넣는다. 말하는 구간이면 인식기를 돌려 부분 텍스트와 확정 텍스트를 만든다.
3. **번역 스레드**: 부분 텍스트는 최신 1건만 담는 칸에서, 확정 텍스트는 큐에서 꺼내 번역한다. 확정 텍스트를 먼저 처리한다.
4. **화면**: 공유 상태(확정 줄 최근 2개 + 진행 중인 줄)를 읽어 그린다. 상태가 바뀌면 다시 그리기를 요청한다.

### 화면 동작
- **오버레이**: 화면 아래쪽 가운데. 확정 자막은 흰색 글자에 검은 외곽선, 진행 중인 자막은 흐린 색. 확정 자막은 5초 뒤 사라진다.
- **제어 창**: 시작/정지 버튼, 원문 언어 선택(영어/일본어, 정지 상태에서만 바꿀 수 있다), 원문 함께 보기 체크박스, 오류 메시지 한 줄. 창을 닫으면 프로그램이 끝난다.
- 오류(출력 장치 없음, 모델 파일 없음)는 제어 창에 보여 주고 정지 상태로 돌아간다.

## 파일 구성
- `Cargo.toml`: `sherpa-onnx`, `wasapi`, `eframe`, 0단계에서 고른 번역 crate
- `src/main.rs`: 실행 인자 처리(GUI / `--console` / `--bench-translate`)
- `src/pipeline.rs`: 캡처·인식·번역 스레드 연결, 자막 상태
- `src/audio.rs`: WASAPI loopback 캡처
- `src/asr.rs`: VAD, 구간 재디코딩. 기존 `src-tauri/src/stt.rs`의 VAD·디코딩 부분을 옮겨 썼다
- `src/translate.rs`: 번역 모델 로드와 `translate(&str) -> String`
- `src/overlay.rs`: 자막 오버레이와 제어 창
- `scripts/build.ps1`: CMake·nuget.exe를 PATH에 넣고 cargo 실행
- `scripts/download-models.ps1`: 모델을 `models/`에 받는다. 모델은 저장소에 넣지 않는다
- `README.md`: 새 주제에 맞게 다시 쓴다

### 지울 것
구현을 시작할 때 지운다: `src-tauri/`, `src/main.ts`, `index.html`, `package.json`, `package-lock.json`, `vite.config.ts`, `tsconfig.json`, `scripts/download-model.sh`, `scripts/download-model.ps1`(새 스크립트로 대체), 한국어 인식 모델.

## 진행 단계
1. **0단계**: 모델 후보 측정, 조합 확정.
2. **1단계 (콘솔)**: loopback → 원문 텍스트 → 한국어 텍스트를 표준 출력에 찍는다. 원문 언어는 실행 인자로 받는다. 줄마다 지연 시간을 함께 찍는다.
3. **2단계 (오버레이)**: 자막 오버레이와 제어 창을 붙인다.
4. **3단계 (선택)**: 특정 프로그램 소리만 받기, 글자 크기·위치 설정.

## 확인이 필요한 위험
- **번역 엔진 Windows 빌드**: `ct2rs`는 CMake가 필요하고 `crt-static` 설정이 필요할 수 있다. `sherpa-onnx` 정적 링크와 C 런타임 설정이 충돌하는지 0단계에서 같이 빌드해 확인한다.
- **부분 번역의 흔들림**: 문장 중간까지의 번역은 문장이 끝나면 크게 바뀔 수 있다. 보기 불편하면 부분 번역을 끄고 원문 부분 텍스트 + 확정 번역만 보여 주는 방식으로 바꾼다.
- **배경음**: 음악·효과음이 섞인 대사는 인식 정확도가 떨어진다.
- **전체 화면**: 독점 전체 화면 모드의 플레이어·게임 위에는 오버레이가 보이지 않는다. 테두리 없는 전체 화면(브라우저 전체 화면 포함)은 된다.
- **출력 장치**: 원격 접속 등으로 출력 장치가 없으면 loopback을 열 수 없다.
- **CPU 부하**: 인식과 번역이 동영상 디코딩과 CPU를 나눠 쓴다. 스레드 수를 제한한다.
- **모델 라이선스**: NLLB는 비상업 전용, Moonshine·TranslateGemma는 각자 조건이 있다. 배포하기 전에 고른 모델의 라이선스를 확인한다.

## 범위 밖
- 자막 파일(SRT) 저장, 동영상 파일을 직접 여는 기능
- 영어·일본어 외 원문 언어, 한국어 외 자막 언어
- 화자 구분
- macOS, iOS
- 클라우드 API

## 검증
1. 0단계 결과를 이 문서에 기록한다(고른 조합, 측정값, 이유).
2. `cargo check`, `cargo clippy`를 통과시킨다.
3. 인터넷을 끊고 `cargo run --release`로 띄운 뒤 영어 동영상과 일본어 동영상을 각각 재생해 아래를 확인한다.
   - 대사가 시작되면 목표 시간 안에 번역 자막이 보이고, 문장이 끝나면 확정 자막으로 바뀐다(1단계의 지연 로그로 수치 확인).
   - 30분 연속 재생해도 자막이 점점 밀리지 않고 메모리가 계속 늘지 않는다.
   - 음악만 나오거나 조용한 구간에서는 자막이 나오지 않는다.
   - 오버레이 아래의 플레이어를 마우스로 그대로 조작할 수 있다.
   - 정지를 누르면 자막이 멈추고, 다시 시작하면 이어진다.
   - 모델 파일을 지우고 실행하면 오류 메시지가 보이고 프로그램이 죽지 않는다.
