# anycall 플레이어: 자막이 나오는 동영상 플레이어 (Windows 내장 디코더, Rust)

> 2026-11-12 작성. 기존 계획([PLAN.md](PLAN.md), 시스템 소리 오버레이)은 그대로 두고, 그 위에 플레이어 모드를 더하는 계획이다.

## 목표
동영상 파일을 열면 재생하면서 **한국어 자막**을 보여 주는 가벼운 플레이어를 만든다.

1. 동영상 옆에 **자막 파일이 있으면 그 파일을 쓴다.**
2. 자막 파일이 없으면 음성 언어를 **자동으로 판별**한다.
   - 영어·일본어: 기존 인식·번역 엔진으로 한국어 자막을 만든다.
   - 한국어: 번역하지 않는다.
3. 재생은 Windows 내장 디코더(Media Foundation)에 맡긴다. 따로 배포하는 DLL은 없다.

기존 오버레이 방식과 가장 다른 점은 **소리를 파일에서 직접, 재생보다 앞서 읽는다**는 것이다. 그래서

- 자막을 말이 나오는 시각에 맞춰 띄울 수 있다(기존 방식의 2~3초 지연이 없다).
- 스피커 음소거나 다른 프로그램 소리의 영향을 받지 않는다.
- 부분 번역이 필요 없어 CPU를 덜 쓴다(확정 문장만 번역한다).

| 측정 항목 | 목표 |
|---|---|
| 자막이 뜨는 시각과 말이 시작되는 시각의 차이 | ±0.3초 이내 |
| 파일을 연 뒤 재생이 시작될 때까지 (자막 파일이 있을 때) | 1초 이내 |
| 파일을 연 뒤 첫 AI 자막이 준비될 때까지 | 10초 이내 (모델 로드 포함) |
| 분석 속도 (대사가 많은 구간) | 재생 속도의 1.5배 이상 |

수치는 0단계에서 이 PC(AMD Ryzen 5 7530U)로 재서 고친다.

## 가정
요청에 없어서 아래처럼 정했다. 다르면 이 절부터 고친다.

- **한국어 음성**: 자막을 띄우지 않는다. 한국어를 받아쓰려면 한국어 인식 모델이 따로 필요해서 이번 범위에 넣지 않는다.
- **외국어 자막 파일만 있을 때**(예: `영화.en.srt`): 요청대로 그 파일을 그대로 보여 준다. 자막 글을 번역하는 기능은 5단계 선택 항목으로 둔다.
- **자막 파일**은 동영상과 같은 폴더, 같은 이름의 파일만 찾는다. MKV 안에 들어 있는 자막 트랙은 1차 범위에서 뺀다(Media Foundation이 쉽게 꺼내 주지 않는다).
- **한 파일의 음성 언어는 하나**로 본다. 두 언어가 섞인 영상은 다루지 않는다.
- **기존 오버레이 모드는 남긴다.** `anycall --overlay`로 실행한다. 인식·번역 코드를 함께 쓰므로 유지 비용이 작다.
- 대상 OS는 Windows 10 2004 이상 x64, GPU 없이 CPU만 쓴다(기존과 같다).

## 결정 사항

### 재생: `IMFMediaEngine`
- `windows` crate(이미 `wasapi`가 0.62.2를 끌어온다)에 `Win32_Media_MediaFoundation` 기능을 켜서 쓴다.
- 디코딩, 하드웨어 가속, 소리 출력, 소리·화면 동기화는 모두 Media Engine이 한다. Rust 쪽은 열기·재생·일시정지·탐색·볼륨·현재 위치 조회만 한다.
- 영상은 Media Engine이 **전용 Win32 창에 직접 그린다**(HWND 모드). 프레임을 Rust로 가져와 복사하지 않는다.

### 화면 구성: 영상 창 + 투명 egui 창
- 영상 창 위에 지금의 투명 egui 창을 같은 크기로 겹친다. 이 창이 자막과 조작 막대를 그리고 마우스·키보드 입력을 받는다.
- egui 창은 "항상 위" 대신 **영상 창의 소유 창**으로 만든다. 그러면 영상 창 바로 위에만 머물고 다른 프로그램을 가리지 않는다.
- 자막 그리기(`outlined`)와 글꼴 설정은 `overlay.rs`의 코드를 그대로 쓴다.
- 이 구성이 창 이동·크기 조절·전체 화면에서 어긋나지 않는지는 0단계에서 확인한다. 안 되면 프레임을 받아 egui 텍스처로 그리는 방식(프레임 서버 모드)으로 바꾼다. 그 방식은 프레임 복사 때문에 CPU를 더 쓴다.

### 자막용 소리: `IMFSourceReader`
- 같은 파일을 소리 전용으로 한 번 더 연다. 재생과 독립이라 재생 위치보다 앞서 읽을 수 있다.
- 16kHz 모노 float로 받는다. Source Reader가 변환해 주지 않으면 채널을 직접 합치고 `sherpa_onnx::LinearResampler`(이미 wav 입력에 쓴다)로 바꾼다.

### AI 자막: 미리 읽기 파이프라인
```
[SourceReader] --샘플+시각--> [VAD 구간] --> [인식] --> [번역] --> [큐 저장소] <--현재 위치-- [화면]
   소리 디코딩                  침묵 0.4초·최대 6초      확정만         (시작, 끝, 한국어, 원문)
```
- 기존 `Segmenter`·`Recognizer`·`Translator`를 쓴다. 달라지는 점은 두 가지다.
  - 시각을 `Instant`(실제 시간)가 아니라 **파일 안의 샘플 위치**로 센다.
  - 부분 텍스트와 부분 번역을 만들지 않는다. 구간이 끝나면 한 번 인식하고 한 번 번역한다.
- 결과는 큐 `(시작, 끝, 한국어, 원문)`로 저장소에 쌓는다. 화면은 재생 위치에 해당하는 큐를 찾아 그린다. 자막 파일도 같은 저장소 형식으로 읽어 들이므로 화면 코드는 하나다.
- 분석은 재생과 무관하게 파일 끝까지 계속한다(낮은 스레드 우선순위). 이미 분석한 구간으로 되돌아가면 바로 나온다.
- **탐색**: 분석하지 않은 위치로 건너뛰면 분석도 그 위치로 옮긴다. 저장소는 분석을 마친 구간 목록을 함께 갖는다.
- **분석이 재생을 못 따라갈 때**: 늦게 완성된 큐는 원래 끝 시각이 지나지 않았으면 보여 주고, 지났으면 건너뛴다. 조작 막대에 "자막 준비 중"을 표시한다.

### 언어 자동 판별
- sherpa-onnx의 음성 언어 판별(`SpokenLanguageIdentification`, Whisper tiny 다국어 모델)을 쓴다. Rust crate 2.0.1에 API가 있다. 모델은 `download-models.ps1`에 추가한다.
- 파일의 **세 지점**(처음, 30%, 60% 부근)에서 말소리 구간을 각각 몇 초씩 모아 판별하고 다수결로 정한다. 오프닝 음악이나 한 장면의 외국어 대사에 속지 않게 하려는 것이다.
- 결과에 따른 동작:

| 판별 결과 | 동작 |
|---|---|
| 영어, 일본어 | 해당 언어 인식 모델로 AI 자막을 만든다 |
| 한국어 | 자막 없음. 인식·번역 모델을 올리지 않는다 |
| 그 밖의 언어, 판별 실패 | 자막 없음. "지원하지 않는 언어"를 표시하고 수동 선택을 안내한다 |

- 조작 막대에서 **자동 / 영어 / 일본어 / 끄기**를 직접 고를 수 있다. 판별이 틀렸을 때 쓴다.

### 자막 파일
- **찾는 순서**(동영상이 `영화.mp4`일 때): `영화.ko.*`·`영화.kor.*` → `영화.*`(언어 표시 없음) → 그 밖의 언어 표시(`영화.en.*` 등).
- **형식**: SRT, SMI, VTT, ASS/SSA. ASS는 글만 뽑고 위치·효과 태그는 버린다. SMI에 언어가 여럿이면 한국어(`KRCC`)를 고른다.
- **글자 인코딩**: BOM이 있으면 그대로, 없으면 UTF-8로 읽어 보고 깨지면 CP949로 읽는다(`encoding_rs`). 한국어 SMI는 CP949가 많다.
- 자막 파일을 창에 끌어다 놓으면 그 파일로 바꾼다. 조작 막대에서 **파일 자막 / AI 자막 / 끄기**를 바꿀 수 있다.
- 자막 싱크 조절 키(±0.5초)를 둔다.

### 지원하지 않는 코덱
이 PC를 조회한 결과 HEVC 디코더가 없고 DTS 소리 디코더가 없다. 10비트 H.264도 내장 디코더가 지원하지 않는 것으로 알고 있다(0단계에서 파일로 확인).
- 영상을 열 수 없으면 원인(코덱 이름)과 해결 방법(HEVC는 스토어 확장)을 창에 보여 준다.
- 영상은 나오는데 소리 디코딩만 실패하면 재생은 계속하고 "AI 자막을 만들 수 없음"을 표시한다.

## 0단계: 위험한 부분부터 확인 (구조를 만들기 전에)
작은 시험 코드로 아래 네 가지를 확인하고 결과를 이 문서에 "0단계 결과" 절로 적는다.

1. **창 겹치기**: Media Engine이 그리는 Win32 창 위에 투명 egui 창을 소유 창으로 겹친다. 창 이동, 크기 조절, 최대화, 전체 화면, 다른 창으로 전환했을 때 어긋나거나 깜빡이지 않는지 본다.
2. **소리 읽기**: Source Reader로 MP4(AAC), MKV(AC-3, Opus) 소리를 16kHz 모노로 읽는다. 읽는 속도(재생 속도의 몇 배인지)와 탐색 정확도를 잰다.
3. **언어 판별**: 한국어·영어·일본어 영상 각 3개 이상으로 정확도, 판별 시간, 모델 크기를 잰다. 음악이 깔린 장면과 오프닝 곡에서 틀리는지 본다.
4. **분석 속도**: 대사가 많은 영어·일본어 영상 2~3분을 미리 읽기 방식으로 돌려 재생 속도의 몇 배로 분석되는지 잰다(`--file-bench`). 이 PC에서 번역은 문장당 2~3.5초(float32)라서 여기가 가장 빠듯하다.

결과에 따른 진행:
- 1이 안 되면 프레임 서버 모드로 바꾼다.
- 4가 재생 속도보다 느리면 재생 전에 미리 분석해 두는 시간을 두거나, 번역 모델을 더 작은 것으로 바꾸는 방안을 사용자와 정한다.

## 구현 단계
각 단계는 끝에 적은 방법으로 확인한 뒤 다음으로 넘어간다.

1. **플레이어 기본**: 파일 열기(대화상자, 끌어다 놓기, 실행 인자), 재생·일시정지, 탐색 막대, 볼륨, 전체 화면, 키보드(Space, ←/→ 5초, ↑/↓ 볼륨, F, Esc). 조작 막대는 마우스를 움직이면 나타난다.
   - 확인: MP4·MKV·WebM 파일이 소리와 함께 재생되고 탐색·전체 화면이 된다. 지원하지 않는 파일은 오류 문구가 나온다.
2. **자막 파일**: 찾기, 네 형식 읽기, 인코딩 판별, 큐 저장소, 화면 표시, 싱크 조절.
   - 확인: 형식·인코딩별 시험 파일(UTF-8 SRT, CP949 SMI, ASS, VTT)을 읽는 단위 시험. 실제 영상에서 자막 시각이 맞는다.
3. **AI 자막**: Source Reader 입력, 미리 읽기 파이프라인, 탐색 대응, 준비 상태 표시. 언어는 우선 수동으로 고른다.
   - 확인: 자막 파일이 없는 영어·일본어 영상에서 자막이 말과 ±0.3초 안에 뜬다. 앞뒤로 탐색해도 자막이 이어진다. 30분 재생에서 밀림과 메모리 증가가 없다.
4. **언어 자동 판별**: 세 지점 판별, 결과별 동작, 수동 선택.
   - 확인: 0단계의 시험 영상에서 한국어는 자막 없이 재생되고, 영어·일본어는 선택 없이 자막이 나온다.
5. **마무리(선택)**: 만든 AI 자막을 `.ko.srt`로 저장, 외국어 자막 파일의 글을 번역해 보여 주기, 마지막 재생 위치 기억.

## 파일 구성
- `Cargo.toml`: `windows`(Media Foundation, 창, 셸 대화상자 기능), `encoding_rs` 추가
- `src/main.rs`: 실행 인자(`anycall [파일]` 플레이어 / `--overlay` 기존 모드 / `--console` / `--file-bench`)
- `src/player.rs`: Media Engine 감싸기, 영상 창, 재생 제어
- `src/player_ui.rs`: 투명 egui 창(자막, 조작 막대, 입력). `overlay.rs`의 그리기 함수를 함께 쓴다
- `src/media_audio.rs`: Source Reader로 16kHz 모노 샘플 읽기, 탐색
- `src/cues.rs`: 큐 저장소(시각으로 찾기, 분석한 구간 목록)
- `src/subfile.rs`: 자막 파일 찾기, SRT·SMI·VTT·ASS 읽기, 인코딩 판별
- `src/langid.rs`: 언어 판별
- `src/pipeline.rs`: 미리 읽기 모드 추가(샘플 위치 기준 시각, 확정만 처리)
- `src/asr.rs`: `Segmenter`가 샘플 위치로 구간 시각을 내도록 확장
- `scripts/download-models.ps1`: Whisper tiny 다국어 모델 추가

## 위험
- **창 겹치기**가 깔끔하지 않을 수 있다(창을 끌 때 자막 창이 한 박자 늦게 따라오는 등). 0단계 1번에서 판단한다.
- **분석 속도**: AMD에서는 번역이 Intel보다 느리다. 대사가 빽빽한 영상은 분석이 재생을 간신히 앞설 수 있다.
- **언어 판별 오류**: 노래, 배경 음악, 짧은 대사에서 틀릴 수 있다. 수동 선택으로 보완한다.
- **코덱**: HEVC, DTS, 10비트 H.264 파일은 재생이 안 되거나 소리가 안 난다. 내장 디코더 방식의 한계다.
- **번역 품질**은 기존과 같다(NLLB 600M). 미리 읽기라서 구간을 더 길게 잡아 문맥을 늘릴 여지는 있다(0단계 4번에서 함께 본다).
- **라이선스**: Whisper 모델은 MIT다. NLLB(비상업)와 Moonshine 일본어 모델(비상업) 조건은 기존과 같다.

## 0단계 결과 (2026-11-12)
측정 환경: AMD Ryzen 5 7530U, Windows 11 Home(빌드 26300), 화면 2560×1600(150%). 실제 대사가 있는 동영상이 없어서 시험 영상을 만들어 쟀다(`testdata/`, 저장소에 넣지 않음).
- 영상: ffmpeg `testsrc`(1280×720 30fps). 소리: Windows TTS(영어 Zira, 한국어 Heami) 2~3분, 일본어는 모델에 든 실제 음성(합 70초)을 반복. 앞에 8초짜리 화음+잡음을 붙여 "오프닝 음악"을 흉내 냈다.
- 형식별: MP4(H.264+AAC), MKV(H.264+AC-3), WebM(VP9+Opus), MKV(AV1+Opus), MKV(HEVC), MKV(10비트 H.264), MKV(DTS).

### 1. 창 겹치기: 통과
- Media Engine(HWND 모드)이 그리는 영상 창 위에 투명 egui 창을 소유 창(`GWLP_HWNDPARENT`)으로 겹쳤다. 창 이동·크기 조절·최대화·전체 화면·Esc 복귀에서 자막 창이 영상 창 클라이언트 영역에 맞게 따라갔다(스크린샷으로 확인).
- **egui는 glow(OpenGL) 렌더러를 써야 한다.** 기본 wgpu는 Windows에서 투명 창을 합성하지 못해 흰 배경이 된다. 기존 오버레이 모드도 glow로 바꿨다.
- Media Engine에는 D3D11 장치(`MF_MEDIA_ENGINE_DXGI_MANAGER`)와 출력 형식(BGRA)을 준다(Microsoft 예제와 같은 구성).
- 창을 끄는 동안 자막 창이 한 박자 늦는지는 눈으로 보지 못했다(스크립트로만 옮겼다).

### 2. 소리 읽기: 통과
| 파일 | 소리 | 읽기 속도(재생 대비) | 탐색 |
|---|---|---|---|
| MP4 | AAC | 236~273배 | 정확(앞 키 프레임 기준 ±16ms) |
| MKV | AC-3 | 176~202배 | 앞 키 프레임으로 감(10초 → 8.3초). 앞부분을 잘라 내 정확히 맞췄다 |
| WebM | Opus | 206배 | 위와 같음 |
| MKV | DTS | — | 디코더가 없어 읽지 못함 |
- Source Reader가 16kHz 모노 float로 바로 변환해 준다(직접 리샘플할 필요 없었다. 안 되는 경우를 위해 직접 변환하는 길도 남겨 뒀다).

### 3. 언어 판별: 통과 (Whisper tiny)
| 파일 | 결과 | 시간 |
|---|---|---|
| 영어 TTS, 영어 실제 음성 | en | 1.3초 |
| 일본어 실제 음성(AC-3, Opus, m4a) | ja | 1.3~1.4초 |
| 한국어 TTS, 한국어 실제 음성 | ko | 1.2~1.6초 |
| 중국어 실제 음성 | zh(그 밖의 언어) | 1.4초 |
| 음악만 | 말소리 없음 | 0.7초 |
| 앞 12초만 영어, 나머지 한국어 | 지점별 en·ko·ko → ko | 1.2초 |
- 처음에 영어 TTS가 ko로 나왔는데, TTS가 시스템 언어(ko-KR) 때문에 한국어 목소리로 영어를 읽은 것이었다(판별은 맞았다). 영어 목소리로 다시 만든 뒤에는 en.
- Whisper base(약 150MB)도 결과가 같아 tiny(약 100MB)를 쓴다. `ANYCALL_LANGID_MODEL=base`로 바꿀 수 있다.
- 모델 로드 약 1초. 실제 영화(배경 음악, 짧은 대사)로는 아직 재지 않았다.

### 4. 분석 속도: 통과
| 파일 | 길이 | 분석 시간 | 재생 대비 | 큐 |
|---|---|---|---|---|
| 영어 TTS(대사 연속) | 172초 | 45초 | 3.1배 | 30개 |
| 일본어 실제 음성 | 78초 | 27초 | 2.95배 | 15개 |
- 모델 로드 6~7초를 빼면 재생과 동시에 시작해도 늦은 큐가 하나도 없었다.
- 번역이 병목이다(문장당 1~3초, float32). 대사가 이보다 빽빽한 영화는 3배보다 느릴 수 있다.
- **메모리**: 플레이어 프로세스가 약 3.2GB를 쓴다. 대부분 float32로 풀린 번역 모델이다(AMD에서만. Intel은 int8).

### 계획과 달라진 점
- egui 렌더러를 wgpu에서 glow로 바꿨다(위 1번).
- 분석은 소리를 끝까지 먼저 읽고 인식한 뒤, 번역은 별도 스레드가 순서대로 한다. "여기까지 큐가 다 나왔다"는 위치를 따로 알려 탐색 막대에 분석한 구간을 그리고, 아직 분석하지 않은 위치를 재생하면 "자막 준비 중"을 띄운다.
- AI 큐는 말이 끝난 뒤 0.6초 더, 최소 1.5초 보여 준다. 화면에는 최근 두 줄까지만 둔다.
- Moonshine 일본어 모델이 글자마다 공백을 넣는 경우가 있어 인식 결과에서 일본어 사이 공백을 지운다.
- DTS 소리가 든 파일은 영상도 재생되지 않는다(Media Engine이 소리 디코더를 못 찾으면 전체가 실패한다). 원인과 함께 알리기만 하고, 소리 트랙만 끄고 재생하는 것은 남은 일로 둔다.

| 단계 | 상태 | 확인한 방법 |
|---|---|---|
| 0단계 | 끝 | 위 결과 |

| 5. 마무리(선택) | 안 함 | |

남은 일
- 실제 영화·애니메이션(영어·일본어 각 2~3분 이상)으로 인식·판별 정확도와 자막 시각(±0.3초) 확인. 시험 영상은 TTS라 실제보다 쉽다.
- 30분 이상 재생: 메모리 증가, 분석 밀림.
- DTS 파일에서 소리 트랙만 끄고 영상 재생.
- 창을 마우스로 끌 때 자막 창이 따라오는 모습, 다중 모니터·DPI가 다른 모니터로 옮길 때.

## 개발을 이어받는 쪽을 위한 메모 (2026-11-12 현재 상태)
이 계획을 쓰기 전 작업에서 알아낸 것들이다. 다시 알아내지 않아도 되게 적어 둔다.

### 개발 환경 (이 PC)
- AMD Ryzen 5 7530U, Windows 11 Home, GPU 가속 없음. 저장소는 `C:\kwang\anycall`.
- Rust stable 1.99.1(MSVC)과 Visual Studio Build Tools 2022(C++ 워크로드, CMake 포함)를 설치했다. `cargo`는 `%USERPROFILE%\.cargo\bin`에 있다.
- 빌드는 `.\scripts\build.ps1`(= `cargo build --release`), 검사는 `.\scripts\build.ps1 clippy --release`. 첫 빌드는 약 10분, 그 뒤는 20초 안팎이다.
- 모델은 `models/`에 받아 두었다(`.\scripts\download-models.ps1`). 영어·일본어 시험용 wav가 각 모델 폴더의 `test_wavs\0.wav`에 있다.
- 소스 파일은 CRLF 줄바꿈이다.

### 커밋하지 않은 변경
- `src/translate.rs`, `src/main.rs`, `README.md`: Intel이 아닌 CPU 대응(아래).
- `src/audio.rs`: **임시 진단 코드**가 들어 있다(`ANYCALL_DEBUG_AUDIO`, `ANYCALL_DEBUG_NATIVE` 환경 변수를 줄 때만 동작). 음소거 문제 확인이 끝나면 지운다.

### Intel이 아닌 CPU에서의 번역
- CTranslate2는 Intel이 아닌 CPU에서 MKL을 끄고, 그러면 int8 모델을 열지 못한다("Requested int8 compute type…" 오류).
- `CT2_USE_MKL=1`로 MKL을 켜면 열리지만 int8 연산이 매우 느리다(문장당 45~90초). float32는 문장당 2~3.5초다. 스레드를 늘려도 차이가 없다.
- CTranslate2는 `CT2_USE_MKL`을 `main`보다 먼저 읽어 둔다. 실행 중에 `_putenv_s`로 넣어도 반영되지 않는 것을 확인했다. 그래서 `translate::prepare_backend()`가 `main` 맨 앞에서 이 값을 붙여 자기 자신을 다시 실행한다(작업 관리자에 프로세스가 둘 보인다).
- 계산 방식은 `translate::select_compute_type()`이 고른다(Intel은 int8, 그 밖은 float32). `ANYCALL_CT2_COMPUTE`로 강제할 수 있다.
- float32의 메모리 사용량은 재지 않았다.

### 기존 오버레이 모드에서 확인한 것
- 스피커가 **음소거**되어 있으면 loopback으로 받는 소리가 전부 0이라 자막이 나오지 않는다(이 PC에서 측정). 음소거를 풀었을 때 정상 동작하는지는 사용자가 확인하기로 했고, 결과는 아직 듣지 못했다.
- wav 파일 입력(`--console en --wav 파일`)으로는 영어·일본어 모두 인식과 번역이 된다.

### 이 계획과 관련해 확인한 것
- `sherpa-onnx` crate 2.0.1에 `SpokenLanguageIdentification`(Whisper 기반)이 있다(`spoken_language_identification.rs`).
- `windows` crate 0.62.2를 직접 의존성으로 넣고 Media Foundation·D3D11·셸 대화상자 기능을 켰다(Cargo.toml).
- 이 PC의 디코더: H.264, VP8/VP9, AV1, MPEG-4, WMV, MJPEG, AAC, MP3, FLAC, Opus, Vorbis, ALAC, AC-3/E-AC-3은 있다. **HEVC는 없다.** DTS는 디코더가 없다. MPEG-2는 확장은 설치되어 있으나 디코더 조회로는 확인하지 못했다.
- 실행 파일은 `models` 폴더를 실행 파일 위치에서 위로 올라가며 찾는다(`main.rs`의 `find_models_dir`).
